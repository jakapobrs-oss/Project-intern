# การวิเคราะห์และออกแบบระบบ

> ร่างเนื้อหาภาษาไทย · ฐาน: `internship-book-materials.md` §6–7, §10 · ER diagram มีไฟล์รูปแล้วที่ `assets/er-diagram.png`

ในบทนี้กล่าวถึงการวิเคราะห์ความต้องการของระบบ เครื่องมือที่ใช้ และการออกแบบระบบในด้านสถาปัตยกรรม ฐานข้อมูล และส่วนติดต่อโปรแกรม (API)

## 3.1 การวิเคราะห์ความต้องการของระบบ

**ความต้องการเชิงหน้าที่ (Functional Requirements):**
- จัดการเนื้อหาสื่อ (อัปโหลด/อนุมัติ/จัดหมวด)
- จัดผังการแสดงผลแบบหลายโซน (presentation/layout)
- กำหนดตารางการแสดงผลตามช่วงเวลาและกลุ่มจอ
- ควบคุมจอโทรทัศน์ระยะไกล (เปิด/ปิด/เปลี่ยนสัญญาณ)
- ประกาศเหตุฉุกเฉินที่แทรกตารางปกติได้ทันที
- จัดการผู้ใช้และสิทธิ์การเข้าถึง (RBAC)
- เฝ้าระวังสถานะอุปกรณ์และบันทึก audit log

**ความต้องการที่ไม่ใช่เชิงหน้าที่ (Non-functional Requirements):**
- ความปลอดภัย (การยืนยันตัวตน สิทธิ์ และการตรวจสอบย้อนหลัง)
- ความทนทานต่อเครือข่ายขัดข้อง (offline-friendly ผ่าน manifest)
- ความง่ายในการติดตั้งและดูแล (Docker)
- ใช้เทคโนโลยี Open Source

ระยะเวลาดำเนินงานรวมประมาณ 16 สัปดาห์ แบ่งงานหลักออกเป็น 7 ระยะ ดังตารางที่ 3.1

## 3.2 เครื่องมือที่ใช้ในการพัฒนา

### 3.2.1 ฮาร์ดแวร์ (Hardware)
- เครื่องคอมพิวเตอร์สำหรับพัฒนาและทดสอบระบบ (Developer PC)
- อุปกรณ์แสดงผลที่ใช้ทดสอบ: เว็บเบราว์เซอร์ในโหมดเต็มจอ (kiosk) บนเครื่องคอมพิวเตอร์ ทำหน้าที่เป็นจอแสดงผลของระบบ
- การทดสอบการควบคุมจอโทรทัศน์: ใช้ตัวจำลอง (emulator) ที่ผู้จัดทำพัฒนาขึ้น ร่วมกับพอร์ตอนุกรมเสมือน (virtual serial port) แทนจอโทรทัศน์จริง เนื่องจากข้อจำกัดด้านอุปกรณ์ในช่วงพัฒนา (รายละเอียดในหัวข้อ 3.5.3)

### 3.2.2 ซอฟต์แวร์ (Software)
- ภาษา/เฟรมเวิร์ก: Python 3.12 + FastAPI, Node.js + Next.js + TypeScript
- ฐานข้อมูลและบริการ: PostgreSQL 16, Redis 7, MinIO
- เครื่องมือพัฒนา: Visual Studio Code, Git/GitHub, Docker

## 3.3 การออกแบบระบบ

### 3.3.1 สถาปัตยกรรมระบบ (System Architecture)
ระบบประกอบด้วยส่วนหลัก 6 ส่วนที่ทำงานร่วมกันใน Docker stack ได้แก่ (1) Backend (FastAPI) ให้บริการ REST API และตรรกะทางธุรกิจ (2) Worker (Arq) สำหรับงานเบื้องหลัง (3) PostgreSQL ฐานข้อมูลหลัก (4) Redis สำหรับ cache และคิวงาน (5) MinIO สำหรับจัดเก็บไฟล์สื่อ และ (6) Admin UI (Next.js) สำหรับผู้ดูแล โดยส่วนแสดงผล (Player) จะดึงไฟล์ manifest จาก backend แล้วเล่นเนื้อหาแบบ offline-friendly ดังรูปที่ 3.1

### 3.3.2 การออกแบบฐานข้อมูล (ER Diagram)
ฐานข้อมูลประกอบด้วยตารางประมาณ 13 ตาราง (entity 12 ตาราง + ตารางความสัมพันธ์แบบ M:N) แบ่งเป็น 5 กลุ่ม ได้แก่ Identity & Audit, Devices, Content & Composition, Playlists & Schedules และ Emergency ดังรูปที่ 3.2

[[FIG|3.2|file:assets/er-diagram.png|แผนภาพความสัมพันธ์ของข้อมูล (ER Diagram)|big]]

### 3.3.3 แนวคิดลำดับชั้นเนื้อหาแบบ 5 ระดับ (5-Tier Content Hierarchy)
ระบบออกแบบลำดับชั้นเนื้อหาเป็น 5 ระดับ คือ Content (สื่อดิบ) → Zone (โซนแสดงผล) → Presentation (ผังการจัดวาง) → Plan (ลำดับการเล่น) → Schedule (เวลาและกลุ่มจอ) แนวคิดนี้ทำให้สามารถนำเนื้อหากลับมาใช้ซ้ำได้ และการแก้ไขตารางครั้งเดียวมีผลกับทั้งกลุ่มจอ

### 3.3.4 การออกแบบส่วนติดต่อโปรแกรม (API)
API เวอร์ชัน v1 มีทั้งหมดประมาณ 66 endpoints จัดเป็น 13 กลุ่ม (auth, users, devices, groups, contents, presentations, plans, schedules, player, tv, emergency, led, reports) ออกแบบตามแนวทาง REST ยืนยันตัวตนด้วย JWT และมีเอกสารอัตโนมัติแบบ OpenAPI (Swagger)

## 3.4 วิธีการพัฒนา

พัฒนาด้วยกระบวนการแบบวนซ้ำเป็นเฟส (iterative) ใช้ Git/GitHub ในการจัดการเวอร์ชันโค้ด มีระบบ Continuous Integration (GitHub Actions) สำหรับรันการทดสอบและตรวจสอบความปลอดภัยอัตโนมัติ และใช้ Docker เป็นสภาพแวดล้อมการพัฒนาที่สอดคล้องกับ production โดยผู้จัดทำทั้งสองคนแบ่งความรับผิดชอบตามตารางที่ 1.1 และตกลงรูปแบบการเชื่อมต่อ (API) ร่วมกันก่อนแยกกันพัฒนาแต่ละฝั่ง

## 3.5 การทดสอบระบบ

การทดสอบระบบแบ่งออกเป็น 3 ระดับ ได้แก่ การทดสอบอัตโนมัติระดับหน่วย การทดสอบแบบ End-to-End บนระบบที่ติดตั้งจริง และการทดสอบการควบคุมจอโทรทัศน์ด้วยตัวจำลอง

### 3.5.1 การทดสอบอัตโนมัติ (Automated Test)
ระบบใช้ pytest ร่วมกับ pytest-asyncio และ pytest-cov มีกรณีทดสอบ 142 กรณีใน 15 ไฟล์ ครอบคลุมการยืนยันตัวตน อุปกรณ์ กระบวนการจัดการเนื้อหา การควบคุมทีวี การประกาศฉุกเฉินและ audit, มิดเดิลแวร์ความปลอดภัย, รายงาน (reports), การควบคุม LED, การป้องกัน SSRF และงานเบื้องหลัง ผลการทดสอบผ่านครบทั้ง 142 กรณี นอกจากนี้ยังมีระบบ CI (GitHub Actions) ที่รันชุดทดสอบดังกล่าวโดยอัตโนมัติทุกครั้งที่มีการแก้ไขโค้ด เพื่อป้องกันข้อผิดพลาดย้อนกลับ (regression)

### 3.5.2 การทดสอบแบบ End-to-End (Smoke Test)
เป็นการทดสอบที่เดินครบทุกขั้นตอนการใช้งานจริงบนระบบที่ติดตั้งด้วย Docker และใช้ฐานข้อมูล PostgreSQL จริง (ไม่ใช่ฐานข้อมูลจำลอง) รวม 10 ขั้นตอน ได้แก่ (1) ตรวจสอบความพร้อมของบริการ (2) เข้าสู่ระบบและต่ออายุโทเคน (3) สร้างและจับคู่อุปกรณ์พร้อมส่งสัญญาณ heartbeat (4) เพิ่มเนื้อหาและอนุมัติ (5) สร้างผังการแสดงผล เพลย์ลิสต์ และตารางเวลา (6) ตรวจสอบไฟล์ manifest ที่ player ได้รับ (7) ประกาศเหตุฉุกเฉินและตรวจสอบการแทรกตารางปกติ (8) คิวคำสั่งควบคุมทีวี (9) การบันทึก audit log และ (10) การล้างข้อมูลทดสอบ ผลการทดสอบผ่านครบทั้ง 10 ขั้นตอน

### 3.5.3 การทดสอบการควบคุมจอโทรทัศน์ด้วยตัวจำลอง (Emulator)
เนื่องจากในช่วงพัฒนายังไม่มีจอโทรทัศน์ที่รองรับ RS-232 ให้ทดสอบ ผู้จัดทำจึงพัฒนาตัวจำลอง (emulator) ขึ้นเพื่อตรวจสอบความถูกต้องของคำสั่งควบคุมโดยไม่ต้องใช้อุปกรณ์จริง ประกอบด้วยตัวจำลองจอโทรทัศน์ที่ถอดรหัส (decode) ไบต์คำสั่งตามสเปกของแต่ละยี่ห้อ ตัวจำลองส่วนแสดงผล และตัวจำลองอุปกรณ์ HDMI-CEC วิธีทดสอบคือให้ระบบสร้างไบต์คำสั่งจริงแล้วส่งให้ตัวจำลองถอดรหัสกลับ เพื่อเปรียบเทียบว่าคำสั่งที่ได้ตรงกับที่สั่งหรือไม่

ผลการทดสอบพบว่าคำสั่งทั้งหมด 47 รูปแบบ ครอบคลุม 6 ยี่ห้อ (Samsung MDC, LG, Sony, Panasonic, NEC, Toshiba) และโหมด HDMI-CEC ถูกถอดรหัสได้ถูกต้องทุกคำสั่ง ไม่พบข้อผิดพลาด และเมื่อทดสอบส่งผ่านพอร์ตอนุกรมเสมือน (virtual serial port) ข้อมูลที่อ่านกลับมาตรงกับที่ส่งไปทุกไบต์ การทดสอบระดับนี้ยืนยันความถูกต้องของการเข้ารหัสคำสั่งตามโปรโตคอล ส่วนการทดสอบกับจอโทรทัศน์จริงยังคงเป็นงานที่ต้องดำเนินการต่อไป (ดูหัวข้อ 5.3)
