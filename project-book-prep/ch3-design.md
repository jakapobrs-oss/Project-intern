# บทที่ 3
# การวิเคราะห์และออกแบบระบบ

> ร่างเนื้อหาภาษาไทย · ฐาน: `internship-book-materials.md` §6–7, §10 · ER diagram มีไฟล์รูปแล้วที่ `assets/er-diagram.png`

ในบทนี้กล่าวถึงการวิเคราะห์ความต้องการของระบบ เครื่องมือที่ใช้ และการออกแบบระบบในด้านสถาปัตยกรรม ฐานข้อมูล และส่วนติดต่อโปรแกรม (API)

## 3.1 การวิเคราะห์ความต้องการของระบบ

**ความต้องการเชิงหน้าที่ (Functional Requirements):**
- จัดการเนื้อหาสื่อ (อัปโหลด/อนุมัติ/จัดหมวด)
- จัดผังการแสดงผลแบบหลายโซน (presentation/layout)
- กำหนดตารางการแสดงผลตามช่วงเวลาและกลุ่มจอ
- ควบคุมจอโทรทัศน์ระยะไกล (เปิด/ปิด/เปลี่ยนสัญญาณ)
- ประกาศเหตุฉุกเฉินที่แทรกตารางปกติได้ทันที
- จัดการผู้ใช้และสิทธิ์การเข้าถึง (RBAC)
- เฝ้าระวังสถานะอุปกรณ์และบันทึก audit log

**ความต้องการที่ไม่ใช่เชิงหน้าที่ (Non-functional Requirements):**
- ความปลอดภัย (การยืนยันตัวตน สิทธิ์ และการตรวจสอบย้อนหลัง)
- ความทนทานต่อเครือข่ายขัดข้อง (offline-friendly ผ่าน manifest)
- ความง่ายในการติดตั้งและดูแล (Docker)
- ใช้เทคโนโลยี Open Source

ระยะเวลาดำเนินงานแสดงด้วยแผนภูมิ Gantt *(รูปที่ 3.1) — [ ] ต้องจัดทำรูป Gantt*

## 3.2 เครื่องมือที่ใช้ในการพัฒนา

### 3.2.1 ฮาร์ดแวร์ (Hardware)
- เครื่องคอมพิวเตอร์สำหรับพัฒนา (Developer PC)
- อุปกรณ์ทดสอบการแสดงผล: Android TV, แท็บเล็ต, Raspberry Pi, เครื่อง Windows

### 3.2.2 ซอฟต์แวร์ (Software)
- ภาษา/เฟรมเวิร์ก: Python 3.12 + FastAPI, Node.js + Next.js + TypeScript
- ฐานข้อมูลและบริการ: PostgreSQL 16, Redis 7, MinIO
- เครื่องมือพัฒนา: Visual Studio Code, Git/GitHub, Docker
- *(รายละเอียดครบทุกเครื่องมือดูที่ `tools-list.md`)*

## 3.3 การออกแบบระบบ

### 3.3.1 สถาปัตยกรรมระบบ (System Architecture)
ระบบประกอบด้วยส่วนหลัก 6 ส่วนที่ทำงานร่วมกันใน Docker stack ได้แก่ (1) Backend (FastAPI) ให้บริการ REST API และตรรกะทางธุรกิจ (2) Worker (Arq) สำหรับงานเบื้องหลัง (3) PostgreSQL ฐานข้อมูลหลัก (4) Redis สำหรับ cache และคิวงาน (5) MinIO สำหรับจัดเก็บไฟล์สื่อ และ (6) Admin UI (Next.js) สำหรับผู้ดูแล โดยส่วนแสดงผล (Player) จะดึงไฟล์ manifest จาก backend แล้วเล่นเนื้อหาแบบ offline-friendly *(รูปที่ 3.2)*

### 3.3.2 การออกแบบฐานข้อมูล (ER Diagram)
ฐานข้อมูลประกอบด้วยตารางประมาณ 13 ตาราง (entity 12 ตาราง + ตารางความสัมพันธ์แบบ M:N) แบ่งเป็น 5 กลุ่ม ได้แก่ Identity & Audit, Devices, Content & Composition, Playlists & Schedules และ Emergency *(รูปที่ 3.3 — มีไฟล์ ER diagram แล้ว)*

### 3.3.3 แนวคิดลำดับชั้นเนื้อหาแบบ 5 ระดับ (5-Tier Content Hierarchy)
ระบบออกแบบลำดับชั้นเนื้อหาเป็น 5 ระดับ คือ Content (สื่อดิบ) → Zone (โซนแสดงผล) → Presentation (ผังการจัดวาง) → Plan (ลำดับการเล่น) → Schedule (เวลาและกลุ่มจอ) แนวคิดนี้ทำให้สามารถนำเนื้อหากลับมาใช้ซ้ำได้ และการแก้ไขตารางครั้งเดียวมีผลกับทั้งกลุ่มจอ

### 3.3.4 การออกแบบส่วนติดต่อโปรแกรม (API)
API เวอร์ชัน v1 มีทั้งหมดประมาณ 66 endpoints จัดเป็น 13 กลุ่ม (auth, users, devices, groups, contents, presentations, plans, schedules, player, tv, emergency, led, reports) ออกแบบตามแนวทาง REST ยืนยันตัวตนด้วย JWT และมีเอกสารอัตโนมัติแบบ OpenAPI (Swagger)

## 3.4 วิธีการพัฒนา

พัฒนาด้วยกระบวนการแบบวนซ้ำเป็นเฟส (iterative) ใช้ Git/GitHub ในการจัดการเวอร์ชันโค้ด มีระบบ Continuous Integration (GitHub Actions) สำหรับรันการทดสอบและตรวจสอบความปลอดภัยอัตโนมัติ และใช้ Docker เป็นสภาพแวดล้อมการพัฒนาที่สอดคล้องกับ production

## 3.5 การออกแบบการทดสอบ

ระบบใช้ pytest ร่วมกับ pytest-asyncio และ pytest-cov มีกรณีทดสอบประมาณ 133 กรณีใน 15 ไฟล์ ครอบคลุมการยืนยันตัวตน อุปกรณ์ กระบวนการจัดการเนื้อหา การควบคุมทีวี การประกาศฉุกเฉินและ audit, มิดเดิลแวร์ความปลอดภัย, รายงาน (reports), การควบคุม LED, การป้องกัน SSRF และงานเบื้องหลัง นอกจากนี้ยังมีการทดสอบแบบ End-to-End (smoke test) และระบบ CI ที่รันการทดสอบอัตโนมัติทุกครั้งที่มีการแก้ไขโค้ด
