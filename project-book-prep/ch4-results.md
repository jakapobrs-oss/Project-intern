# ผลการดำเนินงาน

ในบทนี้นำเสนอผลการพัฒนาระบบจัดการจอประชาสัมพันธ์ดิจิทัล ทั้งในส่วนความสามารถของแต่ละโมดูล หน้าจอการใช้งานจริง และส่วนแสดงผล

## 4.1 ภาพรวมระบบที่พัฒนา

ระบบได้รับการพัฒนาจนสามารถใช้งานได้ครบวงจร ประกอบด้วยส่วน backend (REST API), ส่วนจัดการสำหรับผู้ดูแล (Admin UI) และส่วนแสดงผล (Player) ทั้งบนเว็บและ Android รองรับกระบวนการทำงานตั้งแต่การอัปโหลดเนื้อหา → จัดผังการแสดงผล → ตั้งตารางเวลา → แสดงผลบนจอ → การประกาศเหตุฉุกเฉิน

## 4.2 โมดูลและความสามารถหลัก

ระบบประกอบด้วยโมดูลการทำงานหลักและความสามารถของแต่ละส่วน สรุปได้ดังตารางที่ 4.1

[[TBL|4.1|โมดูลและความสามารถหลักของระบบ]]

| โมดูล | ความสามารถ |
|---|---|
| Auth & Users | ยืนยันตัวตนด้วย JWT + RBAC 7 บทบาท, ล็อกบัญชีเมื่อล็อกอินผิดซ้ำ, รองรับ cookie auth |
| Devices | จับคู่อุปกรณ์ด้วยรหัส, heartbeat, telemetry (CPU/อุณหภูมิ/uptime), จัดกลุ่มจอแบบ M:N |
| Contents | อัปโหลดสื่อ + ตรวจซ้ำด้วย sha256 + สร้าง thumbnail + กระบวนการอนุมัติ (draft→pending→approved/rejected) |
| Presentations | จัดผัง layout หลายโซน (composer) ใน Admin UI |
| Plans | จัดลำดับ presentation พร้อมกำหนดระยะเวลาแสดงผล |
| Schedules | ผูก plan กับกลุ่มจอ + กฎเวลาแบบ RRULE (iCal) + ช่วงเวลารายวัน + ลำดับความสำคัญ + การอนุมัติ |
| TV Control | สั่งเปิด/ปิด/เปลี่ยนสัญญาณผ่าน HDMI-CEC และ RS-232 หลายยี่ห้อ ผ่านคิวใน Redis |
| LED Control | ควบคุมจอ LED ผ่านโมดูลควบคุมเฉพาะ *(ฟีเจอร์เพิ่มเติม)* |
| Emergency | ประกาศฉุกเฉิน override ทุกตาราง + หมดอายุอัตโนมัติ + ต้องการการยืนยันรับทราบ (ack) |
| Reporting | บันทึกประวัติการเล่น (playback_logs) + สรุปรายงานและส่งออกข้อมูล *(ฟีเจอร์เพิ่มเติม)* |
| Monitoring | Prometheus metrics + readiness/liveness + audit log + Sentry + การสำรองข้อมูล |
| Player | แสดงผลหลายโซน + วนเล่นตาม plan + overlay ประกาศฉุกเฉิน + cache แบบ offline |

## 4.3 หน้าจอส่วนจัดการสำหรับผู้ดูแล (Admin UI)

ส่วนจัดการประกอบด้วยหน้าจอหลักหลายหน้า ผู้ใช้เข้าสู่ระบบด้วยชื่อผู้ใช้และรหัสผ่าน (รูปที่ 4.1) จากนั้นระบบแสดงหน้าแดชบอร์ดสรุปสถานะภาพรวม ได้แก่ จำนวนจอทั้งหมดพร้อมสถานะออนไลน์ สื่อที่รออนุมัติ และตารางเล่นที่กำลังทำงาน (รูปที่ 4.2)

[[FIG|4.1|file:assets/ch4/fig-4-01-login.png|หน้าเข้าสู่ระบบ (Login)|big]]

[[FIG|4.2|file:assets/ch4/fig-4-02-dashboard.png|หน้าแดชบอร์ดสรุปสถานะระบบ (Dashboard)|big]]

หน้าจัดการสื่อรองรับการเพิ่มสื่อทั้งแบบไฟล์และ URL โดยสื่อที่เพิ่มใหม่ต้องผ่านกระบวนการอนุมัติก่อนนำไปแสดงผลจริง ผู้มีสิทธิ์สามารถกดอนุมัติหรือปฏิเสธได้จากหน้ารายการโดยตรง (รูปที่ 4.3)

[[FIG|4.3|file:assets/ch4/fig-4-03-contents.png|หน้าจัดการสื่อและการอนุมัติ (Contents)|big]]

การจัดผังการแสดงผลทำผ่าน presentation ซึ่งกำหนด layout และเนื้อหาในแต่ละโซน จากนั้นนำ presentation มาเรียงลำดับเป็นเพลย์ลิสต์ และผูกกับกลุ่มจอผ่านตารางเวลาที่กำหนดช่วงเวลาและลำดับความสำคัญ (รูปที่ 4.4–4.6)

[[FIG|4.5|file:assets/ch4/fig-4-05-plans.png|หน้าจัดเพลย์ลิสต์ลำดับการเล่น (Playlists)|big]]

[[FIG|4.6|file:assets/ch4/fig-4-06-schedules.png|หน้าจัดตารางเวลาการแสดงผล (Schedules)|big]]

หน้าจัดการอุปกรณ์แสดงรายการจอทั้งหมดพร้อมสถานะ (ออนไลน์ / ออฟไลน์ / ยังไม่ผูก) รหัสสำหรับจับคู่อุปกรณ์ และเวลา heartbeat ล่าสุดของแต่ละจอ (รูปที่ 4.7) ส่วนหน้าควบคุมจอโทรทัศน์ใช้ส่งคำสั่ง เปิด/ปิดจอ ปรับเสียง และเปลี่ยนช่องสัญญาณ HDMI ไปยังจอที่เลือกผ่าน HDMI-CEC หรือ RS-232 (รูปที่ 4.8)

## 4.4 ส่วนแสดงผล (Player)

ส่วนแสดงผลทำหน้าที่ดึง manifest จาก backend แล้วแสดงเนื้อหาตามผังและตารางที่กำหนด รองรับการแสดงหลายโซนพร้อมกัน การวนเล่นตามลำดับ และการแสดง overlay เมื่อมีประกาศฉุกเฉิน รวมถึงการ cache เนื้อหาเพื่อให้เล่นต่อได้แม้เครือข่ายขัดข้อง

รูปที่ 4.11 แสดงตัวอย่างจอแสดงผลจริงผ่าน web player หลังจับคู่อุปกรณ์กับระบบแล้ว โดยแสดงเนื้อหาเว็บ (แผนที่เส้นทางภายในโรงพยาบาล) เต็มจอตามตารางเวลาที่กำหนด และเมื่อผู้ดูแลสั่งประกาศฉุกเฉิน จอทุกจอที่เป็นเป้าหมายจะแสดง overlay ข้อความแจ้งเตือนแทรกทับเนื้อหาปกติทันที และกลับสู่การแสดงผลเดิมโดยอัตโนมัติเมื่อประกาศถูกยกเลิกหรือหมดอายุ (รูปที่ 4.12)
